# Spring JDBC storage migration (unreleased)

[简体中文](spring-jdbc.md) · [README](../../README.en.md) · [Issue #1](https://github.com/SuanLa/relayq/issues/1)

## Status and scope

This describes the current source, not the published Maven Central `0.1.0`. A new version must be selected before release; do not overwrite `0.1.0`.

Production dependencies of core and starter no longer include MyBatis / MyBatis-Plus. Task, audit, and snapshot stores use `NamedParameterJdbcTemplate`. RelayQ no longer registers ORM mapper scanning, mapper XML, or a MyBatis-Plus customizer, and does not alter host mapper locations.

Unchanged:

- Submission, Handler, and management service APIs, including submission deduplication by `biz_key`.
- The three tables and indexes; no schema migration is required for this change.
- MySQL 8 `FOR UPDATE SKIP LOCKED`, database time, lease renewal/reclaim, owner/status fencing, retries, cancellation, dead-letter redrive, and actionable backlog semantics.
- Existing transaction boundaries for state and audit writes; scheduling wakeup after commit, not rollback.
- Handler responsibility for business-side idempotency. This does not provide exactly-once business side effects such as payments.

No changes to Pod resources, Hikari pool size, metrics cache duration, MySQL durability settings, or scheduling algorithms are included. Capacity tests have not been rerun.

## Consumer migration

1. Continue providing a MySQL JDBC driver, `spring.datasource.*`, and the matching Spring transaction manager. Standard single-DataSource Boot applications can use JDBC Starter auto-configuration. RelayQ reuses the DataSource and pool rather than creating a private one.
2. Hosts using an ORM must declare their own Starter, version, and scanning configuration. Do not remove the business ORM merely because RelayQ is upgraded, or mix incompatible ORM Starters. RelayQ no longer dictates ORM versions, but cannot resolve conflicts within the host's own dependency graph.
3. Host mappers and RelayQ can commit/roll back together when they use the same DataSource and Spring transaction. Multi-DataSource / multi-transaction-manager applications must explicitly select matching infrastructure. This change adds neither automatic routing nor cross-database transactions.
4. Remove mapper scanning, XML locations, and MyBatis-Plus settings used **only for RelayQ**. Preserve business mapper settings; exclude RelayQ's plain storage interfaces from host ORM scanning.
5. The three `core.mapper.*Mapper` names remain, but are now plain storage contracts without `BaseMapper`. Inherited generic operations such as `updateById`, Wrapper queries, and generic task `insert` are removed (audit and snapshot retain explicit `insert`). Domain entities no longer have ORM annotations. Custom integrations using those internal APIs, entity mappings, or old XML need adaptation and recompilation; this is not binary-compatible for internal API consumers.
6. Custom interface beans still override the defaults and must honor transaction, fencing, uniqueness, and return-value contracts. Missing single-row lookups return `null`; empty ID batches execute no SQL; enums bind by name; null audit/snapshot insert fields are omitted to preserve database defaults. IDs remain generated by services.

## Reproducible verification

Requires JDK 21 and Maven. As of 2026-09-15, Testcontainers has been removed. Default builds do not connect to MySQL and report integration tests as skipped. Before explicitly enabling them, configure the connection and obtain authorization for isolated test-table writes/DDL on the specified server.

```powershell
mvn clean verify

# Run separately. Profiles add only test-scope host ORM dependencies.
mvn -pl relayq-spring-boot-starter -am -Pcompat-mybatis '-Drelayq.mysql.tests=true' '-Dtest=JdbcStarterIntegrationTest' '-Dsurefire.failIfNoSpecifiedTests=false' test
mvn -pl relayq-spring-boot-starter -am -Pcompat-mybatis-plus '-Drelayq.mysql.tests=true' '-Dtest=JdbcStarterIntegrationTest' '-Dsurefire.failIfNoSpecifiedTests=false' test

# Without compatibility profiles, the production graph must not contain these components.
mvn -pl relayq-core,relayq-spring-boot-starter -am dependency:tree '-Dincludes=org.mybatis:*,org.mybatis.spring.boot:*,com.baomidou:*'
```

Coverage includes real SQL parameter/enum/NULL/time mapping, duplicate-key translation, ID batches, pagination, submission deduplication, transactional claiming and concurrent skip-locked behavior, reclaim rechecks, renewal and stale writes, retries/dead letters, snapshots, atomic state/audit rollback, after-commit wakeup, and example HTTP end-to-end flows.

The compatibility profiles load real auto-configuration and a business XML mapper from standard MyBatis Starter `3.0.3` and MyBatis-Plus Starter `3.5.17`, separately. They check that host data and RelayQ tasks commit/roll back together, not just that the application starts. They do not promise compatibility with every host ORM version.

Reports are written to each module's `target/surefire-reports/`. The historical 250 QPS README report is unchanged and is not a JDBC performance acceptance result.

## Historical verification record (2026-09-14)

The following results used the former container-based harness. They are not results for the external-MySQL replacement added on 2026-09-15. No database integration rerun is claimed by that replacement.

JDK `21.0.7`, Spring Boot `3.2.9`, MySQL `8.0.36`, Testcontainers `1.21.4`, JVM timezone `Asia/Shanghai`. Full `mvn verify` succeeded: 95 tests passed with zero failures, errors, or skips (core 67, starter 15, example 13). A preceding clean removed stale mapper XML build output.

Each compatibility profile passed 3 tests. An Enforcer rule also prevents reintroducing production MyBatis / MyBatis-Plus dependencies, while allowing test-scope compatibility fixtures.

Existing end-to-end fixtures were corrected: fixed database/profile configuration removed, duplicate redrive checks HTTP 409, and manual snapshots supply a task ID. Business rules were not changed to accommodate tests. No commit, push, artifact publication, or operation on existing Kubernetes/databases was performed.
